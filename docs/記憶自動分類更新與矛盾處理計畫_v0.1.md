# 記憶自動分類、狀態更新與矛盾處理計畫 v0.1

## 1. 文件目的

本文件規劃 `hela_mem_zh_mvp` 下一階段的記憶寫入決策流程，處理以下五個能力：

1. entity alias normalization。
2. 以相同 entity／memory type／topic 限縮 embedding candidates。
3. 只在規則無法安全判斷時呼叫 AI resolver。
4. 能確認新舊順序與狀態轉移時，自動建立 `supersedes`。
5. 內容互斥但無法可靠判定順序時，建立雙向 `contradicts`。

這是 implementation plan，不代表上述能力已完成。實作應維持目前 namespace 隔離、來源可追溯、固定 embedding 維度與 transaction 內雙向 edge 等既有契約。

---

## 2. 現況與缺口

### 2.1 已有基礎

目前程式已具備：

- `ExtractionResult`、`ExtractedEntity`、`ExtractedMemory` 與 `ResolutionAction` 的嚴格 Pydantic schema。
- `memory_namespaces`、`source_messages`、`ingestion_runs`、`entities`、`memory_entities`、`memories` 與 `memory_edges`。
- `canonical_key(content, memory_type)` 的 exact normalized hash。
- exact duplicate 時執行 `MERGE_PROVENANCE`，否則 `CREATE`。
- extractor 顯式輸出的 `supersedes`／`contradicts` relation 可寫入 edge。
- `semantic`、`co_retrieval`、`contradicts` 由 `upsert_edge()` 在同一 transaction 寫成雙向。
- 寫入完成後，會為新記憶建立有限的 semantic／temporal edges。

### 2.2 尚未完成的核心能力

目前不應被誤認為已有自動更新 resolver，原因如下：

- entity lookup 只比對 `canonical_name` exact match；`aliases` 只是 JSONB 附加資料，沒有 normalized lookup、唯一性或 alias collision contract。
- memory exact key 只移除空白並 `casefold()`；中文異體、全半形、標點、人物別名與 topic synonym 不會收斂。
- `resolve_memory()` 只回傳 `MERGE_PROVENANCE` 或 `CREATE`，不會產生 `SUPERSEDE`／`CONTRADICT`／`IGNORE`。
- semantic neighbor 現在先按 `created_at` 取最近 5 筆，再算 embedding；沒有先按 entity／type／topic 限縮，也不是真正的向量 top-k candidate search。
- extractor relation 只涵蓋同一批 extraction 內的 candidate，不能可靠比較既有資料庫中的舊狀態。
- `MemoryResolutionResult` 已有 schema，但尚未接入 provider、candidate snapshot、post-validation 或 persistence。
- 現有 `topic` 只取 `concepts[0]`，沒有 canonical topic key，也沒有「同一狀態欄位」的明確識別。
- resolver decision、候選清單、模型版本、prompt 版本與判斷依據沒有獨立 audit record。

因此新流程必須放在 extraction 與 `memories` 正式寫入之間，而不是只擴充現有 `_entity()` 或 semantic edge loop。

## 3. 設計原則

### 3.1 規則先行，AI 僅解模糊案例

決策優先序固定為：

```text
strict validation
→ alias/topic normalization
→ exact idempotency
→ scoped embedding candidates
→ deterministic decision
→ ambiguous-only AI resolver
→ deterministic post-validation
→ atomic persistence
```

能由來源 ID、exact canonical key、時間與分數明確判定的情況，不呼叫 AI。

### 3.2 AI 不直接操作資料庫

AI resolver 只收到經裁切的 candidate snapshot，只能回傳受限 decision schema。它不得：

- 產生 SQL、UUID、namespace 或 edge weight。
- 指定候選清單外的 target。
- 改寫來源證據。
- 自行 commit、刪除或覆寫既有記憶。
- 在沒有互斥證據時產生 `SUPERSEDE` 或 `CONTRADICT`。

### 3.3 不靜默覆寫歷史

- `supersedes` 只改變「目前有效狀態」，不刪除舊記憶。
- `contradicts` 保留雙方內容與 provenance。
- alias collision、低信心與 provider failure 必須留在 durable queue，不可硬併或當作成功忽略。

### 3.4 namespace 是硬邊界

alias、entity、candidate search、resolution target、edge 與 audit record 全部必須具有相同 `namespace_id`。任何跨 namespace target 都是 hard failure。

## 4. 核心術語與資料契約

### 4.1 Canonical entity

代表 namespace 內的單一實體，例如：

```text
canonical_name: 潤羽露西亞
entity_type: person
aliases: 露西亞、Rushia、潤羽るしあ
```

canonical entity 是 candidate scope 的必要條件，不以原始文字直接 join。

### 4.2 Canonical topic

topic 應分成：

- `topic_raw`：extractor 原始輸出，保留追溯。
- `topic_key`：normalize 後的穩定 key，例如 `gpu_purchase`。
- `topic_version`：normalizer/taxonomy 版本。

第一版 topic taxonomy 應保持小型、顯式、可版本化。未知 topic 可產生 deterministic slug，但不得用 embedding 自動把不同 topic 永久合併。

### 4.3 State slot

只靠「同 entity／type／topic」仍可能把多個可並存事實視為更新。建議增加：

```text
state_key = entity_id + memory_type + topic_key + attribute_key
```

`attribute_key` 描述可被更新的狀態欄位，例如：

```text
purchase_intent
owned_item
research_priority
favorite_item
current_location
```

若 extractor 無法可靠給出 `attribute_key`，第一版以 `unknown` 進入 AI resolver，不可直接 supersede。

### 4.4 Resolution candidate

resolver 比較單位應至少包含：

```json
{
  "memory_ref": "opaque-ref",
  "content": "目前改研究 CMP 170HX。",
  "memory_type": "decision",
  "topic_key": "gpu_research",
  "attribute_key": "research_priority",
  "status": "active",
  "occurred_at": "2026-03-01T12:00:00+08:00",
  "entity_refs": ["entity-ref"],
  "similarity": 0.87,
  "confidence": 0.95,
  "evidence": ["source-ref"]
}
```

對 AI 使用 opaque refs；真正 UUID 僅由程式在 post-validation 後對回。

## 5. Alias normalization

### 5.1 正規化層次

保留 raw 值，另產生 lookup key。建議順序：

1. Unicode NFKC。
2. 去除前後空白。
3. 連續空白收斂為單一空白。
4. Latin casefold。
5. 將 lookup 用標點與分隔符收斂，但不改寫 canonical display name。
6. 套用 namespace 內顯式 alias map。

不得預設執行：

- 簡繁體自動等同。
- 日文漢字、假名或羅馬字的模糊音譯合併。
- 任意 substring/fuzzy name merge。
- 跨 `entity_type` 合併同名 alias。

這些可能誤合併不同人物，必須由顯式 seed 或 AI-assisted review 產生提案，再經可追溯規則核准。

### 5.2 建議資料表

新增 `entity_aliases`，不要只依賴 `entities.aliases` JSONB：

```text
entity_aliases
- id UUID PK
- namespace_id UUID NOT NULL
- entity_id UUID NOT NULL
- entity_type VARCHAR(32) NOT NULL
- alias_raw TEXT NOT NULL
- alias_normalized TEXT NOT NULL
- source_type VARCHAR(32) NOT NULL
- source_ref TEXT NULL
- confidence REAL NOT NULL
- status VARCHAR(16) NOT NULL
- normalizer_version VARCHAR(32) NOT NULL
- created_at TIMESTAMPTZ NOT NULL
```

必要 constraints：

- FK `(namespace_id, entity_id)` → `entities(namespace_id, id)`。
- unique `(namespace_id, entity_type, alias_normalized)`，禁止同 type 的 alias 靜默指向兩個 entity。
- `confidence BETWEEN 0 AND 1`。
- `status IN ('active','pending','rejected')`。

原 `entities.aliases` 可在過渡期保留為 read model，但 source of truth 應改為 `entity_aliases`。若保留 JSONB，必須由交易內同步或 projection 重建，不能兩邊各自接受寫入。

### 5.3 Alias resolution 規則

```text
exact canonical normalized match
→ active alias normalized match
→ unresolved entity candidate
```

遇到以下 collision 時停止該 candidate 的自動寫入：

- 同 namespace/type/alias 指向兩個 entity。
- extractor canonical name 命中 A，但 alias 命中 B。
- 同一 extraction 內兩個 entity candidate normalize 到相同 key，卻有不同證據或 type。

collision 寫入 resolution queue，不能使用「第一筆」或較高 confidence 靜默決定。

## 6. Embedding candidate generation

### 6.1 Candidate scope

先做結構過濾，再做向量排名。預設條件：

```text
same namespace
AND same memory_type
AND same canonical entity set or at least one primary entity
AND same topic_key
AND status IN ('active', 'uncertain', 'superseded')
```

其中 primary entity 應由 `memory_entities.mention_role = 'subject'` 或 extractor 的明確欄位決定。現有 `mention_role` 尚未填入，需先補 extractor/schema 與寫入流程。

當 candidate 沒有 entity 時：

- 不可做跨 namespace 或全庫模糊更新。
- 可限縮為同 type + topic + source session 的小型候選。
- 若仍沒有可靠 scope，預設 `CREATE` 並標記 `resolution_scope=no_entity`，不自動 supersede。

### 6.2 向量查詢

使用 pgvector cosine distance，禁止「先按 created_at 取 5 筆再逐筆 dot product」。建議查詢概念：

```sql
SELECT m.id,
       1 - (m.embedding <=> :candidate_embedding) AS similarity
FROM memories m
JOIN memory_entities me ON ...
WHERE m.namespace_id = :namespace_id
  AND m.memory_type = :memory_type
  AND m.topic_key = :topic_key
  AND me.entity_id = ANY(:entity_ids)
  AND m.status IN ('active', 'uncertain', 'superseded')
ORDER BY m.embedding <=> :candidate_embedding,
         m.occurred_at DESC NULLS LAST,
         m.external_id ASC
LIMIT :resolver_candidate_limit;
```

第一版建議：

```text
resolver_candidate_limit = 8
exact_merge_similarity = 0.96
ambiguous_similarity_min = 0.72
```

數值只是初始待校正參數，應放入 `config.yaml`，不能散落在程式碼。上線前以標註資料調整，不把 0.96 當成跨模型通用真理。

### 6.3 分數不直接等於決策

embedding 只決定「值得比較的候選」，不得單獨證明：

- 兩筆是同一事實。
- 一筆比另一筆新。
- 內容互斥。
- 新記憶取代舊記憶。

即使 similarity 很高，也必須通過 entity/type/topic/state slot 與內容相容性規則。

## 7. Deterministic resolver

### 7.1 決策順序

每筆 extracted memory 依序判斷：

1. evidence/message id 是否已處理且 hash 相同。
2. canonical key 是否 exact match。
3. alias 是否成功對到 canonical entity。
4. 是否取得合法 scoped candidates。
5. 是否存在明確的相同事實、互斥事實或更新序列。

### 7.2 可直接決定的案例

| 條件 | action | 寫入結果 |
|---|---|---|
| canonical key exact match | `MERGE_PROVENANCE` | 合併 message refs/confidence，不新增 memory |
| 沒有 candidate | `CREATE` | 新增 `active` memory |
| 同 state slot、語義等價且非互斥 | `MERGE_PROVENANCE` | 保留原 content，附加 provenance |
| 同 topic 但不同 state slot，可同時成立 | `CREATE` | 可建立 semantic/supports，不改舊狀態 |
| 同 state slot、互斥、時間順序可靠 | `SUPERSEDE` | 較新 → 較舊；較舊為 `superseded` |
| 同 state slot、互斥、順序不可靠 | `CONTRADICT` | 雙向 edge；衝突集合進 `uncertain` |
| 無可保存事實或證據不合格 | `IGNORE` | 只留 decision audit，不建立 memory |

`IGNORE` 僅限內容本身無記憶價值、重複噪音或 contract 明確不接受；provider failure、alias collision 與不確定衝突不能用 `IGNORE` 隱藏。

### 7.3 可靠時間的定義

時間來源優先序：

1. 記憶內容明確且有 evidence 支持的事件時間。
2. source message 的 `occurred_at`。
3. ingestion `created_at` 只能代表進資料庫時間，不代表事件順序。

可建立 `supersedes` 必須同時符合：

- same namespace。
- same canonical entity。
- same `memory_type + topic_key + attribute_key`。
- 內容互斥或明確表示狀態變更。
- 新舊時間皆存在且可比較。
- 時間差超過設定 tolerance，或文字含有可驗證的順序訊號（例如「後來」、「現在改成」）。
- resolver confidence 達 `supersede_confidence_min`。

若只知道 ingestion 先後，不符合上述條件。

### 7.4 遲到資料

若新輸入其實描述較早狀態：

- 不得以「這次比較晚寫入」讓它 supersede 現有 active memory。
- 若兩者互斥且既有 memory 事件時間較晚，建立 `existing → incoming` 的 `supersedes`。
- incoming 保存為 `superseded`，仍可供 historical query 召回。

## 8. Ambiguous AI resolver

### 8.1 呼叫條件

只在以下情況呼叫：

- similarity 位於 ambiguous band。
- 同 state slot 候選超過一筆。
- 內容可能等價、更新或矛盾，但規則不能安全區分。
- extractor 的 `attribute_key` 不明確。
- 文句具有否定、條件、未來意圖、轉述或時間指示詞，需要語境判讀。

alias collision 不由 memory AI resolver 自動解決；它屬於 entity resolution queue。

### 8.2 AI 輸入

輸入只包含：

- candidate memory 及逐字 evidence。
- 正規化後 entity/type/topic/attribute。
- 最多 8 筆 scoped existing candidates。
- 每筆候選的狀態、事件時間、source time、similarity 與必要 provenance refs。
- 明確決策定義與禁止事項。

不得傳整個 namespace、無關對話或測試 oracle。

### 8.3 AI 輸出 schema

建議將目前 `ResolutionDecision` 擴充為：

```json
{
  "schema_version": "memory-resolution-v2",
  "candidate_ref": "new-1",
  "action": "SUPERSEDE",
  "target_refs": ["existing-2"],
  "relationship": "same_state_changed",
  "effective_order": "candidate_after_target",
  "confidence": 0.93,
  "reason": "新證據明確表示後來不再購買。",
  "evidence_quotes": ["我最後沒有買 RTX 3090"],
  "needs_review": false
}
```

必要 enum：

```text
action:
  CREATE | MERGE_PROVENANCE | SUPERSEDE | CONTRADICT | IGNORE | DEFER

effective_order:
  candidate_after_target | candidate_before_target | same_time | unknown
```

新增 `DEFER`，讓模型能明確表示資訊不足；不可逼模型在 CREATE/SUPERSEDE/CONTRADICT 中猜一個。

### 8.4 Post-validation

AI 回傳後必須由程式重新驗證：

- target 全在本次 candidate snapshot。
- target namespace/entity/type/topic/state slot 一致。
- evidence quote 能在 supplied source 或 existing provenance 找到。
- `SUPERSEDE` 不能搭配 `effective_order=unknown`。
- `CONTRADICT` 必須有內容互斥證據。
- `MERGE_PROVENANCE` 只能指向一筆等價記憶。
- confidence 低於門檻時改為 `DEFER`，不執行破壞狀態的 action。

模型錯誤、timeout、schema failure 或 post-validation failure 時，candidate 留在 queue；不得自動降級成 `CREATE active`，避免把未解衝突事實暴露為目前狀態。

## 9. Supersedes 與狀態轉移

### 9.1 Edge 方向

沿用既有契約：

```text
newer/current memory --supersedes--> older/replaced memory
```

`supersedes` 是 directional，不建立反向 edge。

### 9.2 狀態更新

成功執行 `SUPERSEDE` 時，在同一 transaction：

1. 建立 incoming memory。
2. 將 incoming 設為 `active`。
3. 建立 incoming → target 的 `supersedes`。
4. 將 target 設為 `superseded`。
5. 若 target 已 supersede 更舊 memory，保留整條歷史鏈。
6. 寫入 resolution decision 與 before/after snapshot。

若 incoming 比 target 更舊，方向反轉：既有 target → incoming，incoming 直接為 `superseded`。

### 9.3 多 active 防線

對可更新的 state slot，transaction 完成時最多一筆 `active`。建議使用：

- `state_key` 欄位。
- partial unique index：同 namespace/state_key 只允許一筆 `active`。
- row lock 或 PostgreSQL advisory transaction lock，key 由 namespace + state_key 決定。

不具 state slot 的事件型記憶可多筆 active，不套此唯一限制。

### 9.4 禁止形成 cycle

寫入前檢查：

- target 不可等於 source。
- target 不可已透過 `supersedes` path 指回 source。
- 同一 state chain 依 effective time 必須單調。

任何 cycle attempt 都應 rollback 並進 resolution error audit。

## 10. Contradicts 與不可判定順序

### 10.1 建立條件

建立 `contradicts` 必須是：

- same state slot。
- 兩個命題無法同時成立。
- 沒有足夠證據判斷哪一個較新或較可信。

「embedding 相似但內容不同」不等於矛盾；可並存的多個偏好、事件或描述也不是矛盾。

### 10.2 Edge 與 status

沿用既有雙向 materialization：

```text
A --contradicts--> B
B --contradicts--> A
```

當衝突會影響 current state，且沒有另一筆已解決的 active state 時：

- A、B 均設為 `uncertain`。
- retrieval 可作歷史或衝突背景，但 current query 不得將任一方當成確定事實。
- answer layer 必須能看到 conflict refs，回覆「目前記憶互相衝突，無法確認」。

若矛盾只存在於歷史來源，但已有更晚且已確認的 active state：

- 保留 contradicts edge。
- 不把已確認 active state 降為 uncertain。
- 舊衝突節點維持 `superseded` 或 `uncertain`。

### 10.3 後續解消

新證據可解消矛盾時：

- 不刪除原 contradicts edge；metadata 增加 `resolved_at`、`resolution_decision_id` 與 `resolution_type`。
- 新 active memory 可 supersede 衝突集合中的舊狀態。
- 原始 contradiction 仍保留供 audit 與 historical query。

## 11. Staging、audit 與 idempotency

### 11.1 不直接把模糊 candidate 寫成 active memory

新增 durable staging：

```text
memory_candidates
- id
- namespace_id
- ingestion_run_id
- candidate_key
- extraction_payload
- normalized_payload
- embedding VECTOR(2560)
- status: pending | resolving | resolved | deferred | failed
- attempt_count
- created_at / updated_at
```

以及：

```text
memory_resolution_decisions
- id
- namespace_id
- candidate_id
- resolver_kind: deterministic | ai
- resolver_model
- resolver_schema_version
- prompt_version
- candidate_snapshot_hash
- action
- target_memory_ids
- confidence
- reason
- evidence_quotes
- validation_status
- before_state / after_state
- created_at
```

### 11.2 Idempotency key

`candidate_key` 建議由以下穩定欄位 hash：

```text
namespace_id
+ extraction_schema_version
+ sorted evidence_message_ids
+ normalized content
+ memory_type
+ normalized entity refs
+ topic_key
+ attribute_key
```

同 key 重跑必須取得同一 staging record；已 resolved 時不得重建 memory/edge。

### 11.3 Snapshot revalidation

AI 呼叫不得持有 DB transaction。流程：

1. 短 transaction 讀取 candidates 並產生 snapshot hash。
2. 關閉 transaction，呼叫 AI。
3. 開新 transaction，lock state slot。
4. 重查 candidates 與 active state。
5. hash 不同則丟棄舊 decision，重新排程。
6. 相同才套用 decision、status 與 edges。

這能避免並行 ingestion 在 AI 等待期間讓判斷過期。

## 12. 模組與 migration 規劃

### 12.1 建議模組責任

```text
normalization.py
  Unicode、alias lookup、topic key、state key

candidate_store.py
  memory_candidates 與 candidate snapshot persistence

candidate_search.py
  entity/type/topic scoped pgvector query

resolver.py
  deterministic decision、AI request building、post-validation

resolution_store.py
  lock、CAS revalidation、decision/edge/status atomic apply

memory_store.py
  保留 namespace/source/entity/memory persistence primitive

edges.py
  維持 edge direction、symmetry、cycle checks
```

避免繼續把 extraction、candidate search、semantic edge、state mutation 全部塞入 `write_ingestion()`。

### 12.2 Schema 變更

建議新 migration 依序：

1. 新增 `entity_aliases`。
2. `memories` 新增 `topic_raw`、`topic_key`、`topic_version`、`attribute_key`、`state_key`。
3. 建立 scoped candidate query indexes。
4. 新增 `memory_candidates`。
5. 新增 `memory_resolution_decisions`。
6. 視 state slot coverage 加 partial unique active-state index。

migration 必須先做 nullable/backfill，再收緊 constraint。不可在未稽核舊資料時直接新增 active-state unique index。

```yaml
  event_time_tolerance_seconds: 60
  max_ai_attempts: 2
  resolver_schema_version: memory-resolution-v2
  prompt_version: resolver-zh-v1
```

所有 threshold 都必須被 Pydantic 驗證：

```text
0 <= ambiguous_similarity_min < exact_merge_similarity <= 1
0 <= confidence thresholds <= 1
candidate_limit >= 1
max_ai_attempts in [1, 3]
```

模型名稱仍由既有 `.env`/Settings 管理；artifact 只記 model id，不記 API key。

## 14. 實作階段

### Phase 0：建立標註集與現況基線

- 從現有 GPU fixture 擴充 30～50 組 pair/group。
- 標記 `MERGE`、`CREATE`、`SUPERSEDE`、`CONTRADICT`、`DEFER`。
- 包含 alias、否定、遲到資料、同 topic 可並存、多 entity 與缺時間案例。
- 保存目前 resolver 結果，證明現況只有 exact merge/create。

產出：fixtures、baseline report、threshold calibration input。

### Phase 1：Alias/topic/state normalization

- 實作純函式 normalizers 與 version contract。
- 建立 `entity_aliases` migration 與 collision detection。
- 補 `mention_role`、`topic_key`、`attribute_key`、`state_key` schema。
- 既有資料先 dry-run backfill，輸出 collision 與 unknown report。

Gate：任何 alias collision 不自動合併；重跑 normalization deterministic。

### Phase 2：Scoped embedding candidates

- 將現有 recent-5 Python dot product 改為 PostgreSQL scoped pgvector top-k。
- 保存 candidate rank、similarity 與 scope reason。
- 對無 entity/topic 的 case 採保守 fallback。

Gate：100% candidate 不跨 namespace；不同比較 slot 不進 resolver shortlist。

### Phase 3：Deterministic resolver

- 實作 decision matrix、時間規則、遲到資料與 idempotency。
- 加入 staging 與 decision audit。
- 暫不啟用 AI，ambiguous 全部 `DEFER`。

Gate：exact/clear cases precision 應優先於 coverage；不得誤產生 supersedes。

### Phase 4：Ambiguous AI resolver

- 使用既有 `StructuredProvider`，新增 `memory-resolution-v2`。
- 實作 opaque refs、prompt、post-validation、retry 與 failure queue。
- AI 呼叫與 DB transaction 分離，套用前 snapshot revalidation。

Gate：所有 action 均通過 target/evidence/order validation；provider failure 不產生 active memory。

### Phase 5：Atomic state/edge application

- 加 state slot lock、supersedes cycle check、active uniqueness。
- transaction 內套用 memory、status、edge、decision audit。
- contradiction resolution metadata 不刪歷史 edge。

Gate：故障注入下不可留下單向 contradicts、半套 status 或 orphan decision。

### Phase 6：離線 backfill 與有限 rollout

- 先 `report-only` 掃描既有 namespace。
- 產出 proposed merges/supersedes/contradicts，不寫正式 state。
- 人工檢查 precision 後，只對測試 namespace啟用 apply。
- 最後才以 namespace allowlist 漸進啟用 live ingestion。

Gate：backfill 可重跑、proposal deterministic、rollback 不需刪除來源資料。

## 15. 測試矩陣

### 15.1 Unit tests

- Unicode NFKC、空白、casefold 與標點 normalization。
- alias exact match、type boundary、collision。
- topic/attribute/state key deterministic。
- candidate filter 不跨 namespace/entity/type/topic。
- 時間來源優先序與 tolerance。
- 每個 deterministic action。
- `SUPERSEDE + unknown order` 被拒絕。
- contradicts symmetry 與 supersedes direction。
- supersedes cycle detection。
- AI schema、target refs、evidence quote 與 confidence post-validation。

### 15.2 Integration tests

- 新狀態較晚：new → old supersedes，old 變 superseded。
- 遲到舊資料：existing → incoming supersedes。
- 無法判定順序：雙向 contradicts，current answer 不選任一方為確定事實。
- 同 topic 可並存事實：只 CREATE，不互相 supersede。
- alias 命中 canonical entity 後才找到正確候選。
- provider timeout/schema error：candidate deferred，正式 memory/state 不變。
- AI 等待期間 active state 被其他 transaction 更新：snapshot invalidation 並重排。
- 同一 ingestion 重跑：memory/edge/decision row count 不增加。
- transaction 中途失敗：所有 memory/status/edge/audit 一起 rollback。

### 15.3 Quality evaluation

至少回報：

```text
alias resolution precision / collision count
candidate recall@8
candidate cross-slot contamination rate
merge precision
supersede precision / recall
contradict precision / recall
defer rate
AI invocation rate
AI invalid-decision rate
current-state accuracy
idempotency violations
p50 / p95 resolution latency
```

第一版建議 hard gates：

- namespace leakage = 0。
- invalid target apply = 0。
- one-way symmetric edge = 0。
- supersedes cycle = 0。
- idempotency violation = 0。
- provider failure 後 active-state mutation = 0。
- 人工標註集的 supersede precision >= 0.95。
- 人工標註集的 contradict precision >= 0.90。

recall 不足可進 `DEFER`；不得用降低 precision 換取自動化比例。

## 16. CLI 與 artifact

建議新增安全入口：

```powershell
uv run python -m hela_mem_zh_mvp.cli resolve --namespace <key> --dry-run
uv run python -m hela_mem_zh_mvp.cli resolution-report --namespace <key> --output results/resolution
uv run python -m hela_mem_zh_mvp.cli backfill-resolution --namespace <key> --report-only
```

預設皆不做 live state mutation。真正 apply 必須使用明確旗標與 namespace allowlist，例如：

```powershell
uv run python -m hela_mem_zh_mvp.cli resolve --namespace <key> --apply
```

artifact 至少包含：

- config/model/schema/prompt versions。
- normalization result。
- candidate shortlist 與 similarity。
- deterministic/AI decision。
- post-validation 結果。
- before/after state。
- created edges 與 deferred reason。

不得包含 API key、Authorization header 或完整無關對話。

## 17. Rollback 與營運安全

- migration 前備份，先在獨立 `hebbian_memory_mvp` database 驗證。
- 每個自動 decision 有 immutable audit record。
- rollback 以 decision id 反向恢復 status/edge metadata，不刪 source message 或 extracted evidence。
- live 啟用採 namespace allowlist 與 feature flag。
- 出現 alias collision、cycle、invalid AI decision 或 active uniqueness violation 時，立即 fail closed。
- AI resolver 可單獨關閉；關閉後 ambiguous case 全部 `DEFER`，deterministic path 繼續運作。

---

## 18. 不納入本階段

- 全自動建立跨語言 alias，無人工/顯式 seed 即永久合併 entity。
- 使用 embedding 相似度直接覆寫記憶。
- 跨 namespace 的人物或記憶合併。
- 自動刪除 superseded/contradictory 記憶。
- 由 retrieval co-retrieval 權重決定真假或時間順序。
- 讓 answer model 回寫 resolution decision。
- 未經 report-only 稽核就對既有資料執行 destructive backfill。

## 19. 完成定義

此階段只有在以下條件全數成立時才算完成：

1. alias lookup 有正規化、唯一性、collision 與 provenance contract。
2. resolver candidates 確實由同 namespace/entity/type/topic/state scope 的 pgvector top-k 產生。
3. deterministic 與 AI resolver 的責任邊界可由 trace 證明。
4. 可判定更新順序時建立方向正確的 `supersedes`，且 active state 唯一。
5. 無法判定順序的互斥內容建立雙向 `contradicts`，不冒充 current truth。
6. ambiguous/provider failure 會 `DEFER`，不靜默 CREATE active 或 IGNORE。
7. 每個 decision 可追到 source evidence、candidate snapshot、model/prompt/schema version 與 DB before/after state。
8. unit、integration、quality gates 與故障注入結果都有 machine-readable artifact。

最終目標不是讓系統「一定做出決定」，而是讓它只在證據足夠時自動更新；證據不足時，可靠地保存矛盾與不確定性。
