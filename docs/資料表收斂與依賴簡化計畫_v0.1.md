# Hebbian Memory 資料表收斂與依賴簡化計畫 v0.2

日期：2026-07-22

範圍：`D:\Hebbian-memory` PostgreSQL schema、SQLAlchemy persistence、ingestion、resolution、retrieval、learning、lifecycle 與 graph projection
本文件性質：現況稽核、已執行 migration 與後續驗證計畫

## 1. 最終方向

目前 22 張 application tables 不是都沒有價值，但長期保存了過多「執行過程、相容副本、歷史 trace、可重建 projection」，使 canonical data、operational state 與 diagnostic artifact 混在同一資料庫。

本計畫改採 **最小可維護核心**：

1. PostgreSQL 只保存不能安全重建、會影響未來回答或仍需繼續處理的資料。
2. 每次執行的 extraction、resolution、retrieval、graph 詳細結果改寫固定路徑 latest-only artifact。
3. `memories` 是唯一 canonical memory；不得再建 1:1 claim 副本。
4. factual relation 與 learned association 明確分表，禁止互相升格。
5. operational table 只保存目前狀態：run 保存 summary/outcomes，candidate 只保存未完成項目與 latest decision。
6. 不保留 retrieval history、graph snapshot history、resolution decision history與 learning event history，除非未來明確新增稽核需求。

目標由原先 16 張再收斂為 **11 張 application tables**：

```text
22 current tables
  - 11 duplicated / historical / rebuildable tables
  = 11 maintained tables
```

這個目標保留完整核心功能：

- 原始訊息可追溯。
- `NO_MEMORY`／失敗／成功 extraction coverage 可查。
- memory 的內容、狀態、時間語義、embedding 與 exact evidence 可查。
- entity alias resolution 可維持 collision safety。
- CREATE／MERGE／SUPERSEDE／CONTRADICT／DEFER 可維持。
- factual／semantic／temporal relation 可維持。
- citation-gated association learning 與 retrieval activation 可維持。
- evaluation、answer/judge、lifecycle report 與 graph rebuild 可維持。

不再把「保留功能」誤解為「永久保留每次執行的每一列歷史」。

## 3. 資料保存邊界

### 3.1 永久 canonical data

必須長期保存，因為刪除後無法可靠重建：

- `source_messages`：原始來源與 content hash。
- `memories`：canonical memory、狀態、時間語義與 embedding。
- `memory_evidence`：memory 對原始訊息的 exact evidence span。
- `entities` / `entity_aliases` / `memory_entities`：entity identity、alias collision 與 memory linkage。
- `memory_relations`：factual、semantic、temporal relation 與 provenance。
- `memory_associations`：目前有效的 learned association aggregate。

### 3.2 Operational latest state

需要保存目前狀態，但不需要永久累積每次歷史：

- `ingestion_runs`：active run、每訊息 outcome、coverage summary 與最新完成狀態。
- `memory_candidates`：只保留 pending、resolving、deferred、failed；resolved candidate 完成 artifact 後可清除。

### 3.3 Latest-only artifacts

重要於診斷與驗證，但可由 canonical DB 或單次執行重新產生：

| Artifact | 責任 |
|---|---|
| `results/pipeline/extraction.json` | 最新逐訊息 extraction 明細 |
| `results/pipeline/extraction_coverage.json` | 最新 coverage summary |
| `results/pipeline/resolution.json` | 最新 resolution decisions／before-after trace |
| `results/pipeline/retrieval.json` | 最新 evaluation retrieval trace |
| `results/ask/retrieval.json` | 最新 interactive ask retrieval trace |
| `results/graph/projection.json` | 最新 graph projection |
| `results/summary.json` | root E2E 最終狀態 |

全部採 atomic overwrite；不建立 `<run_id>` 目錄或 append-only log 作為正式 contract。

### 3.4 明確不保存

在目前需求下，下列資料不是 canonical data：

- 每次 retrieval 的所有 candidate rows。
- 每次 graph rebuild 的 nodes/edges snapshot history。
- 同一 candidate 的全部 resolution attempt history。
- 每次 co-retrieval／feedback 的 learning event history。
- canonical memory 的 1:1 compatibility copy。

若未來需要法規稽核、行為重播或長期比較，必須另案定義 retention 與 audit contract，不先用永久表預留可能性。

## 4. 目前依賴問題

### 4.1 實際 source of truth

目前 `memories` 已是實際權威：

- retrieval 查 `Memory.embedding`。
- resolver 直接讀寫 `Memory.status/modality/temporal_scope`。
- entity linkage、edge、association 與 retrieval item 都參照 `memories.id`。
- `memory_claims` 由 `ensure_claim(memory)` 建立，`sync_claim_view(memory)` 從 memory 同步，且 `legacy_memory_id` 為 1:1 unique。

因此 `memory_claims` 是 compatibility copy，不是 canonical ledger。

### 4.2 現行寫入鏈

```text
source_messages
  └─ ingestion_runs
      ├─ message_extraction_outcomes
      └─ memory_candidates
          ├─ memory_resolution_decisions
          └─ memories ── memory_entities
               ├─ memory_claims ── claim_evidence
               ├─ memory_edges ───────────────┐
               ├─ relation_evidence           │ duplicated relation
               └─ retrieval_items             │
                    └─ retrieval_runs          │
                         └─ association_events ── association_stats

memory_claims + claim_evidence + relation_evidence
  └─ graph_projection_runs ── nodes / edges
```

### 4.3 根因

1. additive migrations 只 expand，沒有完成 contract/drop。
2. canonical 命名與真正同步方向相反。
3. run detail 與 latest state 被拆成永久歷史表。
4. 可重建 projection 被當 durable data。
5. learning event/stat 為未來 replay 能力付出兩張表，但目前沒有保留 history 的需求。
6. retrieval trace 已累積 663 detail rows，卻沒有 production reader。
7. JSON 與 normalized rows 同時保存相同資料。

## 5. 目標 11-table schema

```text
Identity / source
  1. memory_namespaces
  2. source_messages
  3. entities
  4. entity_aliases

Operational state
  5. ingestion_runs
  6. memory_candidates

Canonical memory
  7. memories
  8. memory_evidence
  9. memory_entities
 10. memory_relations

Learned state
 11. memory_associations
```

### 5.1 Owner 與責任

| Table | 唯一責任 | 主要 owner | 不得承擔 |
|---|---|---|---|
| `memory_namespaces` | namespace identity / isolation | namespaces | run history、設定快照 |
| `source_messages` | immutable source message | ingestion input | extraction result、memory state |
| `entities` | canonical entity identity | entity normalization | alias list 副本、memory content |
| `entity_aliases` | normalized alias 與 uniqueness | entity normalization | entity metadata、memory link |
| `ingestion_runs` | run summary + per-message outcomes | ingestion workflow | canonical memory、完整 resolution history |
| `memory_candidates` | unresolved work queue + latest decision | resolution workflow | resolved history archive |
| `memories` | canonical memory + current state + embedding | memory persistence | source原文、relation、alias list |
| `memory_evidence` | memory ↔ source exact evidence | memory persistence | canonical content、state |
| `memory_entities` | memory ↔ entity relation | entity linkage | entity alias、factual relation |
| `memory_relations` | factual/semantic/temporal relation | relation persistence | learned co-retrieval weight |
| `memory_associations` | current learned association aggregate | learning | factual truth、event history |

### 5.2 保留、轉換與移除

| 現行 table | 目標 | 判定 |
|---|---|---|
| `memory_namespaces` | 同名 | 保留 |
| `source_messages` | 同名 | 保留 |
| `ingestion_runs` | 同名，增加 `extraction_outcomes` | 保留並擴責任 |
| `message_extraction_outcomes` | 併入 `ingestion_runs` | 移除 |
| `entities` | 同名，移除 `aliases` JSONB | 保留 |
| `entity_aliases` | 同名 | 保留，alias 唯一來源 |
| `memories` | 同名、唯一 canonical | 保留並升格 |
| `memory_entities` | 同名 | 保留 |
| `memory_candidates` | 同名，增加 latest decision | 保留並擴責任 |
| `memory_resolution_decisions` | 併入 candidate/latest artifact | 移除 |
| `memory_edges` | `memory_relations` | 轉換 |
| `memory_claims` | 無 | 移除 compatibility copy |

## 6. 重要欄位契約

### 6.1 `ingestion_runs`

保留 run header 與 summary，逐訊息 outcome 收斂為明確 JSONB 欄位：

```text
id, namespace_id, status,
extractor_model, extractor_schema_version,
started_at, completed_at,
message_count, created_count, merged_count,
superseded_count, contradicted_count,
ignored_count, error_count,
extraction_outcomes JSONB,
config_snapshot JSONB,
created_at, updated_at
```

`extraction_outcomes` 每個 item 固定包含：

```text
source_message_id, status, reason_code,
provider_attempts, error, schema_version
```

完整 provider payload 只寫 `results/pipeline/extraction.json`，不重複塞入 DB。

Retention：每 namespace 保留 active run、被 deferred candidate 參照的 run，以及最新一次 completed/partial run；其他 completed run 在固定 artifact settled 後清理。

### 6.2 `memory_candidates`

此表是 work queue，不是 audit ledger：

```text
id, namespace_id, ingestion_run_id,
candidate_key, extraction_payload,
normalized_payload, embedding,
status, attempt_count,
latest_decision JSONB,
created_at, updated_at
```

`latest_decision` 保存目前處理所需的 action、target IDs、confidence、reason、validation status、before/after state、resolver/policy versions。全部 attempt history 只存在最新 `resolution.json`。

Retention：只保留 `pending/resolving/deferred/failed`；`resolved` 在 run summary 與 artifact 成功落地後清除。

### 6.3 `memories` 與 `memory_evidence`

`memories` 保留：canonical content、type、topic/state keys、status、modality、temporal scope、importance、confidence、event time、embedding。

`memory_claims` 的下列 1:1 欄位全部不再複製：

- `claim_type` / `object_value` / `predicate_key` / `event_time`
- `confidence` / `importance` / `status`
- `modality` / `temporal_scope` / `state_key`

`memory_evidence`：

```text
id, namespace_id, memory_id, source_message_id,
evidence_text, evidence_start, evidence_end,
extractor_model, extraction_schema_version,
created_at, updated_at
```

新資料 evidence coverage 必須 100%。舊 fixture 若沒有 source message 或 exact span，不得由 content 猜測；報告為 `legacy_without_exact_evidence`。

`memories.source_message_ids` 在 evidence cutover 後移除。`source_session_id` 第一輪暫留，待 temporal query 改為 evidence/source join 並驗證效能後再決定。

### 6.4 Entity

`entities.aliases` JSONB 與 `entity_aliases` 重複。保留 normalized `entity_aliases`，移除 JSONB；canonical name 也建立 `source_type=canonical` alias row，維持一致查找與 collision constraint。

### 6.5 `memory_relations`

```text
namespace_id, source_id, target_id, relation_type,
weight, status, origin, confidence, evidence_refs,
activation_count, last_activated_at, metadata,
created_at, updated_at
```

- factual：`supports/contradicts/supersedes/temporal`。
- derived：`semantic`，必須標明 `origin=scoped_pgvector`。
- learned `co_retrieval` 永遠不得寫入此表。
- resolver/extractor 只呼叫單一 `upsert_memory_relation()`，禁止 evidence/edge 雙寫。

### 6.6 `memory_associations`

只保存 retrieval 真正需要的目前 aggregate：

```text
namespace_id, source_memory_id, target_memory_id,
positive_strength, negative_strength, effective_weight,
activation_count, success_count, rejection_count,
last_activated_at, last_learning_token,
policy_version, evidence_refs,
created_at, updated_at
```

設計取捨：

- 不再保存每次 learning event，因此不能從 DB 重播完整事件歷史。
- 每次 ask 產生 `learning_token`；同 token 更新同 pair 時必須 idempotent。
- row 使用 `SELECT ... FOR UPDATE` 或等效原子 upsert，避免並行遺失更新。
- `effective_weight` 由同一 transaction 依 policy 重算。
- association 只影響 activation score，不改 memory status 或 factual relation。

## 7. Runtime 邊界

### 7.1 Ingestion

```text
source_messages (immutable)
  → ingestion_runs.extraction_outcomes (latest run state)
  → memory_candidates (only unresolved work)
  → memories + evidence + entities + relations
  → resolution/extraction fixed artifacts
```

### 7.2 Retrieval

```text
memories + memory_relations + memory_associations
  → in-memory RetrievalResult
  → answer / citation gate
  → CLI response + fixed retrieval artifact
  → optional atomic association aggregate update
```

retrieval 不再 commit `retrieval_runs/items`。`run_id` 改為 execution-local UUID，只用於 response、artifact 與 learning token，不是 DB FK。

### 7.3 Lifecycle

`lifecycle-report` 直接由 memories、association aggregate 與 frozen clock 計算。report-only proposal 寫 fixed artifact，不寫 `lifecycle_decisions`。只有未來實際支援 lifecycle apply 時，才評估是否把 apply decision 寫入 memory latest state，而不是預先保留 audit table。

### 7.4 Graph

`rebuild-graph` 由 memories、evidence、entities、relations 即時計算並覆寫 `results/graph/projection.json`。projection 是 disposable read model，不參與 retrieval availability，也不回寫 canonical DB。

## 8. 分階段 migration

全部採 expand → verify → switch → contract。任何 drop 都是獨立 revision；本計畫不等於刪除授權。

### Phase 0：Baseline 與保護

- 匯出 table/column/PK/FK/index/check inventory。
- 保存每表 row count、namespace count、checksum、min/max timestamps。
- 保存 5-message semantic canary、resolution scenarios、selected retrieval IDs/scores、learning/lifecycle/graph snapshot。
- 確認 dirty worktree，禁止覆蓋既有 evaluation/retrieval 修改。
- 任一待移除表若在實作前出現新 rows，重做 migration mapping，不沿用目前 0-row 假設。

Gate：DB target、Alembic head、focused tests 與小型 real-data flow 通過。

### Phase 1：Run outcome 與 candidate decision 收斂

Expand：

1. `ingestion_runs` 新增 `extraction_outcomes JSONB`。
2. `memory_candidates` 新增 `latest_decision JSONB`。
3. 從 outcome/decision tables backfill；比較 row count、message coverage、latest decision ordering。

Switch：

- `record_extraction_outcomes()` 只更新 run outcome/coverage。
- resolution writer 更新 candidate latest decision；完整 trace 同步寫固定 artifact。
- resolution report 只查 unresolved candidates 與 latest decision。

Contract：

- drop `message_extraction_outcomes`。
- drop `memory_resolution_decisions`。
- stop writing `lifecycle_decisions`；其 initial-state reason/policy 已存在 candidate payload/latest decision。
- 若 lifecycle rows 非 0 且不能無損映射，停止 contract 等待明確處理，不直接刪。

Gate：每訊息 coverage、NO_MEMORY、FAILED、DEFER 與 before/after state 完全一致。

### Phase 2：Memory/evidence 單一權威

1. `claim_evidence` 新增 nullable `memory_id`，經 `memory_claims.legacy_memory_id` backfill。
2. writer 改為直接寫 memory evidence；短暫雙寫只供 equivalence 驗證。
3. semantic/provenance reader 改讀 memory evidence。
4. `memory_id` 改 `NOT NULL`，rename 為 `memory_evidence`。
5. drop `claim_id`、`memory_claims`、`memories.source_message_ids`。
6. 移除 `ensure_claim()`、`sync_claim_view()` 與 compatibility schema guard。

Gate：memory content/state/embedding、exact span、source FK 與 5-message semantic canary一致。

### Phase 3：Relation 單寫

1. 為 `memory_edges` 補齊 provenance/status 欄位。
2. 經 claim legacy mapping 將 `relation_evidence` backfill 到 edge。
3. 合併 writer 為 `upsert_memory_relation()`。
4. retrieval activation、resolution 與 graph artifact 全部改讀單一 relation。
5. rename `memory_edges` → `memory_relations`，drop `relation_evidence`。
6. 從 constraint/enum 移除 `co_retrieval`。

Gate：relation type/direction、contradiction context、activation path 與 selected IDs 不變。

### Phase 4：Association aggregate-only

1. 由 `association_events` 重算並比對每個 `association_stats` aggregate。
2. 在 stats 增加 `last_learning_token/evidence_refs`，rename 為 `memory_associations`。
3. learning writer 改為 row lock + atomic aggregate update。
4. 同 token 重送、transaction retry、並行更新與正負回饋測試通過。
5. 停止 event writer，確認沒有 reader 後 drop `association_events`。

Gate：目前 effective weight 與 retrieval activation 不變；evaluation mode 仍零學習；citation contract 失敗不更新。

Rollback：drop 前可切回 event/stat；drop 後只能從 contract 前 backup 恢復 event history，因此 destructive migration 前需要明確授權。

### Phase 5：Retrieval 與 graph artifact 化

Retrieval：

1. Retriever 回傳 in-memory result，不建立 DB rows、不 commit caller transaction。
2. evaluation 與 ask 分別 atomic overwrite 固定 retrieval artifact。
3. response/artifact 保持 run ID、rank、scores、selected、activation path 與 latency。
4. 確認無 production reader 後 drop `retrieval_items`、`retrieval_runs`。

Graph：

1. graph 由 canonical tables 即時計算。
2. 保持既有核心輸出，projection ID 由 source snapshot hash deterministic 產生。
3. 同 snapshot 重建 checksum 一致後 drop projection 三表。

Gate：answer/judge、retrieval selected IDs、CLI output、graph checksum 與 temp namespace teardown 不變。

### Phase 6：Entity 與最後清理

1. 比較 `entities.aliases` 與 `entity_aliases`，列出 missing/collision。
2. 所有查找改讀 alias rows，停止寫 aliases JSONB。
3. drop `entities.aliases`。
4. 清除 resolved candidates 與不再需要的 old ingestion runs。
5. 更新 namespace purge，只保留 11-table delete order。
6. 更新 `db.py` schema guard、ORM exports、tests、docs 與 CLI help。
7. 使用 SQL spy／PostgreSQL statement log 證明連續兩次 real-data run 沒有舊表 SQL。

## 9. 驗證矩陣

| 邊界 | 必須證明 |
|---|---|
| DB target | database/user/pgvector 正確，不接受其他 DB |
| Schema | empty DB + current-shape clone upgrade 成功；drop 分 revision |
| Source | message count/hash/content 不變，source table 不存結果狀態 |
| Extraction | run JSON outcome 一訊息一筆；NO_MEMORY 不建立 memory |
| Semantics | modality、temporal scope、status、exact evidence span 不變 |
| Resolution | CREATE/MERGE/SUPERSEDE/CONTRADICT/DEFER 行為與 latest state 不變 |
| Candidate retention | unresolved 保留，resolved 只在 artifact settled 後清理 |
| Retrieval | selected IDs、rank、scores、activation path、latency contract 不變 |
| Retrieval persistence | DB 不再新增 retrieval rows；fixed artifact 可檢查最新結果 |
| Learning | citation-gated、token idempotent、並行原子更新；不建立 factual relation |
| Lifecycle | frozen-clock report 一致，仍為 report-only |
| Graph | 刪 artifact 後可重建，同 snapshot checksum 一致 |
| Cleanup | temp namespace 真 purge；11-table delete order 完整 |
| Public contract | `run`、`ingest`、`ask --learn`、reports、`rebuild-graph` 核心輸出相容 |

驗證順序：

1. schema/model unit tests。
2. migration integration tests。
3. 5-message semantic canary。
4. resolution scenarios。
5. 小型 deterministic retrieval/answer proof。
6. learning idempotency/concurrency、lifecycle、graph rebuild。
7. 完整 E2E 與 cleanup proof。

不得用 unit test 綠燈或 CLI exit 0 取代 semantic、retrieval、learning 與 teardown gate。

## 10. 風險與停止條件

### 10.1 有意接受的取捨

- drop resolution decision table 後，DB 只保留 candidate latest decision。
- drop retrieval tables 後，DB 不支援跨 run retrieval 分析。
- drop association events 後，DB 不支援完整 learning replay。
- drop graph tables 後，只保留最新 projection artifact。

這些不是資料遺失事故，而是本計畫明確選擇「維護目前有效狀態，不維護未被要求的歷史分析能力」。contract/drop 前仍必須保存可回退 snapshot。

### 10.2 必須停止 migration

- 待移除表出現無法映射的重要 rows。
- source/message/evidence checksum 不一致。
- semantic canary 或 resolution state 不一致。
- retrieval selected IDs／rank 超出明確 tolerance。
- learning token 無法保證 retry idempotency 或並行安全。
- artifact 尚未 settled 就要清除 DB rows。
- migration 需要猜測 evidence span、state 或 relation provenance。
- 需要 history/audit 的新需求尚未定義 retention。

## 11. 完成定義

只有同時符合以下條件才算完成：

1. application tables 由 22 張收斂為 11 張，ORM、migration head 與 live DB 一致。
2. 每張表只有一個 owner 與一個主要責任。
3. `memories` 是唯一 canonical memory；不存在 claim/view 雙寫。
4. source、evidence、entity、relation 與 association 邊界可由 FK/constraint 證明。
5. extraction outcome 與 latest resolution 保留，但不再用額外歷史表。
6. retrieval 與 graph 不寫 DB，只寫固定 latest artifact。
7. association 只保存目前 aggregate，具 token idempotency 與並行安全。
